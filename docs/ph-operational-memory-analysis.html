Product analysis · October 10, 2026

From Prompt History
to Operational Memory

Product question: How can ph turn prompts, responses, and analysis into knowledge that helps with the next task handled by an AI agent?

Scope: phStatus: direction approved; Phases 0–3 implementedHorizon: first incremental release
Thesis: ph creates value when it prevents context from being repeated, decisions from being rediscovered, and failed attempts from being repeated. Conversation analysis is a means; the outcome is reliable memory brought into the workflow at the right time.

Starting Point

Available

Work evidence

Prompts and responses are captured with project, tool, and Git context. Memories can retain the IDs of their source prompts.

Available

Project knowledge

Append-only memories, curated summaries, MCP decision saving, and shared retrieval through ph context, chat, and MCP tools.

Gap

No guided workflow

There is no explicit step to prepare a task with relevant prior work and no review step to turn its outcome into verifiable knowledge.

The existing ph evolution plan already established curated memory, MCP, and noise reduction. This proposal makes the operational cycle explicit without replacing those foundations.

Options Considered

OptionBenefitsCosts and risksAssessment
A · Analytics dashboardMakes volume, roles, models, and trends visible; useful for inspecting history.Does not bring knowledge into the workflow. It may optimize metrics that do not reduce repeated work.Not a priority
B · Automatic injection everywhereContext is always available with little user effort.Can add noise, tokens, latency, and stale context to every request. Its usefulness is difficult to establish.Avoid as the default
C · Prepare → work → approveMakes reuse intentional, preserves sources and consent, and uses existing context, memory, and MCP capabilities.Requires a brief user action and a useful proposal summary. Manual promotion adds a step.Recommended
D · Autonomous memory agentCould extract and update knowledge without interrupting the workflow.Harder to control; silent corrections, duplicates, and unapproved decisions could contaminate memory.Consider after testing C

Decision

Build a deliberate, measurable workflow and reuse the current data model in the first release.

Memory becomes useful when a user or agent consults it before acting and can save what it learned with references to the conversations that support it. Do not introduce a new knowledge graph or always-on agent in the first release.

Decision record: direction approved in conversation; implementation details are in the operational memory work plan.

Implementable Workflow

1 · Prepareph prepare "task"
Detect project, retrieve relevant context, identify sources.
2 · WorkThe user or agent completes the task with essential context.
3 · Reviewph close
Propose decisions or procedures with supporting prompt IDs.
4 · PromoteApprove before saving or updating project memory.
  • Prepare: Reuse getProjectContext() and semantic search. Produce a short brief with decisions, gotchas, prior work, and source IDs. State clearly when there is no evidence.
  • Close: Start from recent prompts or an explicitly selected range/session. Propose zero or more decisions and procedures. Show what would be saved and which prompt_ids support it.
  • Approval before promotion: Reuse the existing save_decision and project summary paths, extending them to preserve sources. No permanent update without approval.
  • Lightweight feedback: Later, consider useful / irrelevant / stale feedback for retrieved memories. Existing access counters are not an explicit usefulness judgment.

Trade-offs and Guardrails

Product decisionChoiceReason
When to retrieveOn request through prepare and agent paths explicitly chosen by the userReduces irrelevant additions and keeps the workflow predictable.
What to keepConfirmed decisions and procedures linked to sourcesReduces duplicates and makes a memory auditable and correctable.
Evidence statusDistinguish verified, inferred, and unverified claimsA fluent summary is not proof that a procedure still works.
Cross-project retrievalOut of scope for the first releaseInformation from one project may be false or sensitive in another.

Cost, Rate Limits, and Latency

Prepare

Lexical search and database reads are local. Semantic retrieval may call an Ollama embedding endpoint; there is no cloud generation cost, while latency and availability depend on the server.

Close

Proposal extraction can use one optional LLM call. OpenRouter may incur cost and rate limits; MLX-Serve depends on the tunnel and loaded model. Make the provider explicit and let the user skip proposals.

Brief limits

Apply a configurable character or token budget, show source counts, and truncate raw prompts first. Do not make extra LLM calls whenever the TUI opens.

How to Measure Success

Measure useful reuse, not the volume of analysis:

  • Prepare relevance: the first retrieved memories are relevant to the task and project in judged cases.
  • Reuse rate: the user confirms that prior work changed or accelerated the task.
  • Source reliability: every proposed decision links to verifiable prompts and responses; no source is attributed incorrectly.
  • Workflow friction: prepare and close take few steps and can be skipped.
  • Real task evaluation: expand the retrieval set in docs/evals/context-retrieval-golden.json with work queries from multiple projects.

Usage Check · October 10, 2026

Result: The full workflow worked against an isolated temporary database. Semantic embeddings were unavailable, so prepare clearly fell back to recent project context. close --dry-run showed the selected source without a model call or database changes. With an SSH port forward to Parmenide, interactive close generated a proposal, accepted approval, and saved it with its source prompt ID.

ph context --memories-only then returned the promoted knowledge and source reference. The generated proposal included plausible details beyond the sample evidence, so users should review and edit proposals before approval. All writes were limited to the temporary test database.
