A useful core under too many surfaces

Strength: local capture, SQLite storage, and project-scoped retrieval form a coherent foundation with useful seams.

Flaw: PH keeps adding command, transport, and knowledge workflows faster than it proves which ones users need.

Module Seam Leakage / unwired Deep Module

This review describes the current working tree, including uncommitted operational-memory changes. It does not treat documentation or a passing test suite as proof of adoption.

Current Posture

PH has a strong local-first data path and a meaningful retrieval boundary. Prompt capture remains useful without an LLM; semantic retrieval is optional; user approval gates curated memory writes. In this pass the MCP composition root was reduced to protocol setup, while memory and archive SQL moved behind repositories. The remaining concern is scope: a broad command set still exceeds what the operational workflow has validated.

Rules the system respects

  • SQLite is the source of truth; Ollama and generative providers are optional.
  • Project filters are applied inside semantic retrieval before limiting results.
  • Operational `prepare` is read-only; `close` asks for approval before promotion.
  • CLI and MCP share task-context retrieval and atomic memory promotion use cases.
  • Memory and archive repositories share the existing SQLite connection through the stable PhDB facade.

Rules that are not yet proven

  • The plan's three real tasks across different projects are not evidenced; it records one temporary-database usage check.
  • MCP-only tools still own some search and rendering decisions inside their grouped handler modules.
  • Feature breadth spans history capture, analysis, memory, TUI, MCP, import, archive, and remote sync.
  • Embedding-backed retrieval quality has not been evaluated in this pass.

Verification observed: npm test passed (17 files, 94 tests), npm run lint, npm run build, and `npx tsc --noEmit` all passed. A separate embedding-backed retrieval evaluation was not run.

Candidates / Opportunities for Deepening

These are targeted reductions in real Leakage. They are not a proposal to replace the stack or split every file.

1. Contain product scope until real-use evidence exists

Implemented as a scope gateP0

Evidence: `src/cli.ts:46-155` advertises a wide command set; `src/commands/` has 26 handlers; `README.md` describes capture, imports, analysis, memories, TUI, MCP, archive, and remote sync; `ROADMAP.md` now gates new user-facing work on three real tasks across projects.

Problem

PH now has several overlapping ways to retrieve project knowledge (`context`, `prepare`, chat injection, MCP knowledge checks) plus a separate curation flow. The tool's command count is growing while the core promise—capture useful history and find it again—has no adoption or success measure in the repo. This is product-scope Leakage: every surface needs help, docs, compatibility, and tests.

Solution

Keep the current commands available, state their distinct jobs, and defer new commands, transports, or knowledge workflows until the `prepare → work → close → promote` loop is used on three real tasks in different projects. The gate is now recorded in `ROADMAP.md`; no existing capability was removed.

2. Give knowledge promotion one atomic persistence operation

ImplementedP1

Evidence: the previous implementation issued two writes per proposal. `PhDB.promoteMemories()` now delegates to the memory repository (`src/db/index.ts:473`); the shared provenance and promotion use case is `src/knowledge/promotion.ts`, used by CLI (`src/commands/close.ts:101`) and MCP (`src/mcp/tools/projects.ts:8,21`). A rollback test covers the transaction in `src/db/__tests__/phdb.test.ts`.

Problem

Before this review, staged approval did not guarantee atomic persistence. A failed summary update or later proposal could leave a partial result. The fix now places the approved batch in one SQLite transaction; this candidate is addressed in the current working tree.

Solution

The shared promotion operation accepts the approved proposal batch and writes memories plus aggregate summaries atomically. CLI and MCP use the same operation. Provider generation and interactive review stay outside the transaction; the Seam is the approved proposal batch.

Seam: transport-independent promotion input. Deep Module: persistence owns consistency and exposes one operation with a simple result.

3. Thin the MCP composition root and share cross-transport work

Implemented; handlers remain adaptersP1

Evidence: `src/mcp/server.ts` is now 50 lines. Tool definitions live in `src/mcp/tools/definitions.ts`; prompt, project, and timeline handlers are grouped in `src/mcp/tools/`; formatting is isolated in `format.ts`. `src/knowledge/{task-context,promotion}.ts` centralize shared retrieval and persistence.

Problem

The original server mixed protocol registration, all handlers, retrieval policy, writes, and formatting. The composition root is now small and tool code is local by domain. Some MCP-only search, timeline, and output behavior remains in adapter modules, so the transport boundary is improved but not fully domain-neutral.

Solution

The composition root now owns MCP SDK registration, handler dispatch, and error envelopes. Shared task-context retrieval and memory promotion live under `src/knowledge/` and are called by CLI and MCP. Tool-specific protocols and renderers remain grouped under `src/mcp/tools/`; further extraction should wait for another consumer.

Seam: transport-neutral application operations. Deep Module: reusable project knowledge behavior with a compact input/output contract.

4. Split cohesive persistence behind the PhDB facade

Implemented for memory and archiveP2

Evidence: `src/db/index.ts` is now a 521-line public facade with prompt CRUD, FTS, migrations, and query forwarding. Memory and summary persistence moved to `src/db/memory-repository.ts`; archive persistence moved to `src/db/archive-repository.ts`; vectors remain in `src/db/semantic-index.ts`.

Problem

PhDB previously owned SQL for prompt CRUD, FTS, archives, memories, and summaries in one implementation. Memory and archive SQL now live in cohesive repositories over the same connection. The facade deliberately retains source compatibility; prompt CRUD and FTS remain one group.

Solution

The extraction keeps prompt CRUD/FTS in the facade and moves memory/summary and archive SQL behind internal repositories. All repositories share one SQLite connection; `PhDB` method names and return values stay stable. Avoid widening the repository abstraction until a second adapter needs it.

Top Recommendation

First move · validate the operational workflow

Do not add another memory feature yet

Three structural actions are now in place: a product-scope gate, transport-neutral task-context and promotion operations with grouped MCP modules, and internal memory/archive repositories behind the unchanged PhDB API. Keep `prepare` as a read-only experiment. The remaining product test is three real tasks on different projects; record whether the brief prevented repeated work before adding more features.

Why this comes first: the biggest risk is not that PH lacks another abstraction. It is that summaries, memories, and tool-specific retrieval behavior drift while product value remains unmeasured. A transaction seam protects data now; a usage gate protects the project from building maintenance around an unproven loop.
