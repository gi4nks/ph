PH · PRODUCT + ARCHITECTURE Critical review22 October 2026 CLI-first simplification implemented

PH needs a smaller promise

Strength: PH already captures AI work locally and has the raw material to bring relevant project history back when work resumes.

Flaw: the product exposes a toolbox of capture, search, analysis, memory, analytics, integrations, and sync without proving one repeatable job that makes the whole tool worth using.

Deep module: hides complexity behind a stable job Seam: a useful boundary between responsibilities Leakage: duplicated policy or user-visible complexity Inference: plausible direction, not validated demand

Scope: repository source, docs, and tests on the review branch. The first workspace screen did not materially simplify PH and has been removed. This iteration narrows the daily command surface, removes the Ink/React browser, and consolidates task retrieval. This assessment is not a user study; workflow value and retrieval quality still need real-task validation.

Executive assessment

Your concern is justified by the interface surface, but “too many files” is not the root problem. PH grew from prompt capture into a history browser, a retrieval system, a project-memory writer, an AI wrapper, an MCP server, a remote-sync service, and an analytics suite. Each capability is understandable alone. Together they ask the user to learn what PH is for before they can get value from it. This change reduces the visible choices and removes the unused browser; it does not yet prove that PH saves time on real work.

The strongest candidate promise is: PH remembers relevant decisions from your AI work and brings them back into the next task. This fits the existing local capture and project context foundation. It is still a hypothesis: there is no evidence in the repository that task preparation or memory promotion has become a habit, reduced repeated work, or improved outcomes on real projects.

Product simplification implemented

Running `ph` now prints a concise guide instead of starting an interface. The everyday guide presents capture, search, task-aware context, and recent-work review. `ph context "task"` uses semantic retrieval when configured and falls back to recent project context; `ph prepare` is retained as a compatibility alias. `ph close` defaults to the last three hours. The Ink/React browser and its dependencies have been removed; `ph browse` is a plain-text compatibility alias for recent history.

What changed

The daily surface no longer exposes a long command catalog or a keyboard-driven archive. Task retrieval and the old `prepare` command share one path. Historical prompts are plain text by default.

`src/cli.ts`; `src/commands/context.ts`; removal of `src/ui/` and Ink/React packages

What remains unproven

PH still asks the user to invoke a wrapper or install a native hook, then separately run context retrieval. The code has not been evaluated against a real set of maintainer tasks. The full advanced command catalog also remains for compatibility.

Next evidence: observe whether the four-command workflow is used and whether retrieved context changes the work.

What PH is today

A real foundation

  • Capture paths converge on a local SQLite history. Search, import, and hooks can provide value without an LLM.
  • Project scoping and bounded retrieval are meaningful foundations; task-aware `context` degrades to recent project context when embeddings fail.
  • Curated `close` writes require approval and preserve source prompt IDs. Promotion is atomic through the shared knowledge boundary.
  • MCP composition has been separated from prompt, project, and timeline handlers. The server entry point is now an understandable protocol adapter.
  • CLI commands are split into modules, and memory/archive SQL has repository seams behind the database facade.

The user still assembles the product

  • PH still requires the user to invoke a wrapper or configure a native hook, then separately run `ph context` when they need prior decisions.
  • The old browser is gone, but `ph help --all` still exposes a large maintenance catalog for compatibility.
  • MCP and `ph chat` remain additional integration paths with distinct behavior; they are no longer presented as everyday commands.
  • Prompt analysis can write memory in the background while `close` separately proposes curated memory. A user cannot see a single trustworthy lifecycle from the CLI.
  • PH’s own maintainer is the clearest available test user; the request that PH should be useful to you is stronger evidence than feature-completion counts, but it is not yet structured usage evidence.

Deep findings

1 · The core job needs a default path

Implemented · Needs real-task validation

Problem. The old CLI help placed capture, retrieval, analytics, maintenance, and integrations beside one another. The memory loop required users to learn several overlapping commands and the default action entered a keyboard-heavy history browser.

Change. PH now has a short plain-text entry guide, four daily jobs (capture, search, context, review), and one canonical task-context command. The large browser and its runtime dependencies were removed. Maintenance commands remain available through `ph help --all`.

Remaining work. Observe use on real tasks. The context command is still separate from starting the AI tool, and no evidence yet shows it prevents repeated investigation or saves time.

Leverage: High — fewer decisions at entry.

Locality: High — no terminal UI state or renderer.

Tests: Command-output regression plus observed task outcomes.

Evidence: `src/cli.ts`; `src/commands/context.ts`; package manifest after React/Ink removal; README Quick start.

2 · Memory has competing writers and unclear trust

High priority · Strong evidence

Problem. After capture, detached analysis may classify a prompt and update project memory/summary. Separately, `close` selects up to 12 prompt/response pairs, asks a provider to propose durable facts, and allows approval, edit, skip, or quit. The two paths have different controls; the automated path silently discards errors. Git-state deduplication only checks the latest snapshot and does not establish whether two memories say the same thing. This risks both stale/duplicated memory and hidden failure.

Recommendation. Give durable project knowledge one owner and one visible state transition: candidate → reviewed/approved → active or dismissed. Keep raw history immutable. Either limit background analysis to prompt metadata, or surface its memory writes as candidates for the same review mechanism. Record source IDs, age, project, and confidence, and make replacement/supersession explicit.

Before

Two writers, differing approval rules, incomplete deduplication, and swallowed background errors.

After (proposed)

One candidate queue and a visible, auditable promotion path; capture status is distinct from analysis status.

Leverage: High — trust governs all retrieval surfaces.

Locality: High if encoded in a knowledge lifecycle module.

Tests: Duplicate, supersede, source provenance, retry, and failure visibility.

Evidence: `src/commands/background-analyze.ts:36–71`; `src/background/analyzer.ts:7–25`; `src/commands/close.ts:46–108`; `src/knowledge/promotion.ts`.

3 · Retrieval quality is not yet demonstrated by the offline test

High priority · Strong evidence

Problem. A maintained golden dataset is useful, and the live evaluation script can calculate Recall@5 and MRR with configured embeddings. But the current test named as a retrieval golden-set test checks dataset shape, then verifies ranking using three hand-built vectors and a hand-built query vector. It verifies project scoping and vector ranking mechanics; it does not show that the configured embedding model retrieves the right memories for real tasks. The live model-backed evaluation was not run for this report.

Recommendation. Before betting the product on “relevant memory,” run and publish the model-backed evaluation against judged PH tasks, include a no-embedding baseline and an empty/noise test, and record model/version and results. Ask the maintainer after actual tasks whether the brief saved time or prevented a repeated mistake. Do not call the product “memory that works” based only on plumbing tests.

Before

Test vectors prove SQL ranking; the user-facing quality claim remains unmeasured.

After (proposed)

A repeatable judged evaluation measures useful retrieval and compares it to simple recency/project baselines.

Leverage: High — retrieval is the proposed differentiator.

Locality: High — keep evaluation beside retrieval policy and fixtures.

Tests: Live model eval plus offline deterministic regression.

Evidence: `src/context/__tests__/retrieval-eval.test.ts:17–56`; `scripts/eval-context-retrieval.ts`; `docs/evals/context-retrieval-golden.json`.

4 · The interactive archive hid the useful jobs

Implemented · TUI removed

Finding. The former `BrowseApp` combined filtering, details, editing, rerun, provider selection, delete, settings, and project-context keyboard paths in a 964-line Ink/React screen. Its breadth made history browsing a product of its own and obscured PH’s core jobs.

Change. The browser and its React/Ink dependencies have been removed. Plain `ph` prints a short guide; `ph search` and `ph last` return terminal text. The old `browse` and `search -i` forms remain text-compatible for existing scripts.

Before

One large interactive archive with many keyboard actions.

After

A plain-text CLI with four daily jobs and a separate advanced command reference.

Leverage: High — removes an entire interaction layer and dependency set.

Locality: High — no UI state or terminal rendering layer remains.

Tests: Terminal invocation and plain-text output checks.

Evidence: removed `src/ui/`; updated `src/cli.ts`, `src/commands/search.ts`, `package.json`, and `package-lock.json`.

5 · Operational breadth raises the maintenance bar without a proven core

Medium priority · Worth exploring

Problem. PH includes importers, prompt analytics, clustering, reusability scoring, multiple cleanup modes, embedding maintenance, MCP, HTTP server, and remote synchronization. These are not inherently wrong: some may be essential infrastructure or personal workflows. But they increase install, support, security, and compatibility obligations while the primary outcome remains unvalidated. The HTTP server and remote client are a separate deployment and authentication boundary.

Recommendation. Do a usage and support audit before removal: last use, active user, repeated outcome, failure cost, and whether the feature is needed to deliver the core promise. Defer investment in low-use capabilities; group maintenance commands under a discoverable `admin`/advanced surface only if that reduces choice without hiding a needed task. Keep backward-compatible commands until migration evidence exists.

Before

Every capability is advertised beside core capture and retrieval.

After (proposed)

The front door has few choices; advanced tools remain documented and supportable according to measured use.

Leverage: Medium — lowers cognitive and maintenance load.

Locality: Low to medium — mostly command taxonomy and docs.

Tests: Compatibility tests for retained public commands.

Evidence: `src/cli.ts:42–75`; `src/server/index.ts`; `src/commands/remote.ts`; `package.json` dependencies and public bin.

A simpler product shape

This is a direction to validate, not a presumption that every feature should be removed. The smallest coherent product has three jobs. Capture should disappear into tools the user already runs. Resume should return a short, sourced project brief. Review should let the user keep only durable knowledge. Search and history are supporting tools; maintenance and sync are advanced.

1 · Capture

Remember without ceremony

Hooks and supported wrappers record raw exchanges. Show capture health and avoid implying that analysis has completed when it has not.

Keep: hooks, capture normalization, immutable history. Improve: visible status and error recovery.

2 · Resume

Bring back what matters

One command or landing action uses the current project and task to return concise decisions, open work, and source links. Show an honest recency fallback if semantic retrieval is unavailable.

Unify: `prepare`, task context, selected `context` behavior, and the MCP equivalent.

3 · Review

Keep only durable knowledge

After work, review candidate facts against their sources. Approve, edit, dismiss, or supersede. Raw prompt history remains distinct from trusted project memory.

Unify: `close` and any background-derived memory candidates under one lifecycle.

What “simple” should mean in a real trial

A user can install PH, understand its value, and complete capture → resume → review without learning embeddings, analysis providers, project-memory schemas, or transport choices. The success criterion should be behavioral: on three real tasks in at least two projects, did PH retrieve a fact that changed the next action, prevent a repeated investigation, or save time? Record misses, irrelevant results, setup friction, and whether the user remembered to invoke it. Three tasks are a first signal, not statistical proof.

Top recommendation and sequence

Current direction · make PH useful in daily work

Turn PH from a toolbox into one reliable capture → retrieve → review loop.

The first implementation step is now in place: the everyday surface is plain text, the archive UI is gone, task retrieval has one command, and review has a useful default range. Next, use this path on real tasks, measure whether context changes the work, and then decide which advanced commands should be retired instead of merely hidden. Keep memory writes source-linked and approved while retrieval quality is being measured.

    Measure current commands, active integrations, setup friction, capture failures, and real memory use. Correct PH’s stale agent docs.

    Deliverable: a usage map, not telemetry by default.

  2. 1 · Field trial

    Use the workflow on real tasks across projects. Save brief quality, misses, repeated work avoided, time, and user effort.

    Gate: repeated value without ritual fatigue.

Do not confuse a smaller help screen with a complete product change. The TUI and its dependencies are gone and the default command surface is smaller. Advanced command implementations remain for compatibility; retire them only after checking actual use and integration contracts. The next gate is evidence from real workflows, not another feature count.

Documentation and verification risks

The project’s guide rails disagree

`CLAUDE.md` says CLI parsing uses Commander, lists tables `prompts` and `embeddings`, and suggests `ph capture`; current CLI uses manual dispatch, current storage has additional archive/memory structures and sqlite-vec, and `capture` is not a declared command. It also points to `make build` while package scripts show `npm run build`. This is a concrete risk for both contributors and agents: even good changes can target a fictional architecture.

Evidence: `CLAUDE.md:11–15, 24–31`; `src/cli.ts:42–75`; `package.json: scripts, engines`; `src/db/`.

Tests prove contracts, not adoption

The existing suite is valuable for deterministic behavior and boundaries. The retrieval unit test uses fixed vectors; the live script can test the configured embedder, but model-backed results need to be captured and compared. Neither tests whether the user noticed, trusted, or acted on the context. The architecture report therefore does not treat a green suite as product validation.

Evidence: `src/context/__tests__/retrieval-eval.test.ts:17–56`; `scripts/eval-context-retrieval.ts`; `docs/evals/context-retrieval-golden.json`.

Security and operational boundary: PH stores sensitive prompt/response data. Adding or foregrounding remote sync, broad MCP access, or more background processing expands the trust and support boundary. Keep local-first defaults, make data flow and provider use understandable, and test authorization/configuration for the server before positioning remote sync as ordinary setup.

Usage modes and evidence

Ready for...

Local prompt capture, searchable history, interactive browsing, and opt-in MCP access for users who already understand PH’s commands and configure integrations. `prepare` and `close` provide the technical pieces for a manual memory workflow, with explicit approval before curated promotion.

Still requires integration...

A simple default path for the maintainer; proof that retrieved context improves real tasks; one trustworthy project-memory lifecycle; visible capture/analysis failures; and verified model-backed retrieval results. These are product gaps, not missing command handlers.
